## Current stable baseline

- Cartridge-side proofing visuals are **reintroduced and stable**: `src/document_engine.cpp`'s draw-character path is split into a plain document loop and a proofing-attribute-override loop, so the baseline typing/render loop stays plain when proofing overrides are inactive.
- Host-side proofing metadata is the active foundation feeding that path:
  - `src/mailbox.h`: `FormatRunSpellingIssue`, `FormatRunGrammarIssue` flags.
  - `src/document_engine.cpp`: heuristic proofing ranges (common-typo list, repeated-word, double-space) added into `snapshot.format_runs`.
- ROM source (`tools/fairywriter-rom/main.go`) defines explicit document/proofing attribute constants and consumes per-cell proof maps for spelling/grammar visuals.
- A visual coherence fix is in place in `makeViewport`: when no selection exists, selection start/end are normalized to cursor.
- SNES machine tests assert deterministic document-cell attributes and caret glyph placement/movement invariants.
- Text-selection highlighting is reintroduced in the ROM draw loop (it was silently dropped when the proofing split-path landed). Selection bounds are tracked in dedicated zero-page registers `$50`/`$52` (start-inclusive/end-exclusive), not `$19`/`$1b` as the old, deleted code used — `$19`/`$1b` turned out to be genuinely reused as scratch by both the draw loop's own word-wrap measurement code and title-bar rendering within the same commit/render pass, so a value written there at decode time cannot survive to draw time. Selection renders with the spelling-issue visual style and takes priority over proofing when both apply to the same cell.
- A generated public ODT is wired into automated `ctest` via `CMakeLists.txt`'s
  `fairywriter_document_engine` test registration, exercising chapter
  inference, boundary edits, undo/redo, and save/reload through the production
  reader and writer.
- The document stage is cleared across its complete 30x17/510-cell extent before every render. The clear uses a 16-bit accumulator and index to reset two cells per iteration, preserving the old 240-iteration throughput while eliminating stale glyphs in rows 8-16 after a long-to-short viewport transition.
- The static bar above the document is now a real position track. OAM sprite 1 is a dedicated 8x8 thumb whose X coordinate is derived from committed `bytes_before / total_document_bytes`; 32-bit values are normalized together before the SNES hardware multiply/divide step. The thumb is rewritten only when viewport metadata changes, avoiding a measurable keyboard/render timing regression from redundant per-VBlank writes.
- Latest regression status is green:
  - Production `ctest --test-dir build-arm64 --output-on-failure` =
    **7/7 passed**.
  - `fairywriter_xband_end_to_end` is green; it also passed **10 consecutive

## 2026-07-27 document-plane clear and position-thumb fixes

- Phase 4 was reproduced before repair with a permanent real-machine test: a 300-cell viewport painted cell 250, then a two-character commit left that cell at stale tile `0x78` instead of blank. `clearStage` had an 8-bit `CPX #$F0` bound and never initialized cells 240-509.
- `clearStage` now brackets a paired 16-bit clear with local `REP #$30` / `SEP #$30`, stores `$2020` and `$0808` two cells at a time, and stops at 510. A first one-byte-per-cell implementation was rejected because it delayed the guest enough to lose two queued keystrokes in the end-to-end test; the paired loop fixes the full plane without that throughput regression.
- Phase 5 uses confirmed-free OAM sprite 1 and a new final cartridge tile for an 8x8 track thumb. Position metadata comes directly from viewport offsets 108 (`total_document_bytes`) and 112 (`bytes_before`), with the computed X stored at `$0352` and a dirty byte at `$0353`.
- The first always-rewrite OAM version exposed a render/input phase regression in the existing word-wrap test. OAM state persists, so the final implementation updates sprite 1 only after a committed viewport marks it dirty; the mouse pointer remains refreshed every VBlank.
- The cartridge static-data region moved one additional 256-byte page in this
  pass. The later help-plane shift filled all 554 PPU tile slots available in
  the historical 32 KiB layout. The current 64 KiB two-bank layout has 889
  cartridge slots before its rival-header reservation; VRAM still caps the
  usable total at 1024 tiles.
- Permanent machine coverage checks the long-to-short clear and start/middle/end thumb positions (`x=11/124/237`) plus visible framebuffer movement.

## 2026-07-28 draggable scrollbar

The document-position thumb is a real scrollbar: press or drag anywhere on the
track to move through a long document. It **scrolls the view only** -- the caret
stays put, and the user places it by clicking in the scrolled view, which is also
what ends the scroll. Full detail in `DEVELOPMENT_STATUS.md`.

This is the first thing that decouples the published window from the cursor, so
it touches both sides: a new `CommandScrollToFraction` (0x0110) carrying just the
thumb position, a `force_start` mode in `DocumentEngine::makeViewport`, a bridge
scroll anchor released by any caret or edit command, and status flag bit 4 telling
the cartridge the caret is off-window so it renders none.

Watch for two things if you touch this area: anchoring at the very last character
builds an empty window that `makeViewport` rejects (the forced path backfills to
keep the last screenful full), and the mouse region dispatch is now close enough
to its branch limits that `beqMouseMenu` already needed a JMP trampoline.

## 2026-07-28 pointer reach and optimistic-frame accuracy

Both follow-ups from the vertical-movement work are closed, and the second
surfaced a third defect. Full detail in `DEVELOPMENT_STATUS.md`.

- **Mouse clicks reach all 17 document rows.** The pointer's `CMP #8` row bound
  was stale from when the plane really was 8 rows; the lower half of the document
  was silently unclickable. Row arithmetic, target cell, and drag
  repeat-suppression are all 16-bit now.
- **The local optimistic Up/Down move no longer contradicts what is published.**
  It added or subtracted 30 *characters*, which is one screen row only on an
  exactly-30-wide layout, and the wrong caret really was displayed for a frame.
  `verticalMove` now sets the guest cursor to the index it resolved.
- **The pending key code was overwriting the guest cursor's high byte.**
  `$00`/`$01` is the 16-bit guest cursor but the dispatch parked the key code in
  `$01`, so every keystroke made the cursor `position + keyCode*256` until the
  next viewport commit. Key code moved to `$5b`.

## 2026-07-28 wrap-aware vertical cursor movement

`Up`/`Down` now follow the cartridge's 30-column layout with a sticky desired
column. The cartridge resolves the target cell against its own layout and
publishes an absolute caret position through the same path the mouse uses; the
host needed no changes. Full detail in `DEVELOPMENT_STATUS.md`.

Four blocking defects were fixed to get there, and two of them are worth knowing
about independently:

- **Every mouse click published offset 0.** The publish path read `$0400,X`,
  which nothing in the ROM writes; the real per-character UTF-16 offset tables
  are `$0700`/`$0900`. Mouse click positioning was simply non-functional.
- **The main loop's closing branch was a hand-computed `int8` displacement** that
  silently wrapped once the loop body grew, sending execution mid-instruction. It
  surfaced as an unrelated typing test failing. Never hand-compute a displacement
  in `main.go` -- the `branch()` helper panics on out-of-range.

Eight new SNES-machine regressions cover vertical movement (including sticky
column, clamping onto short lines, edge fallback, shift-extend, resolution past
cell 255, and the pointer offset fix). Full `ctest` 10/10,
`fairywriter_xband_end_to_end` 10 consecutive runs, bundle resynced and verified.

Exposed follow-ups: the pointer still rejects rows >= 8 so clicks in the lower
half of the document do nothing, and the local optimistic Up/Down move no longer
matches what gets published (possible one-frame flicker).

## 2026-07-27 (later session) editing-correctness pass

Full detail in `DEVELOPMENT_STATUS.md`. Three defects fixed in
`tools/fairywriter-rom/main.go`, each verified by rebuilding the ROM with and
without the fix:

1. The word-fit check's 8-bit `column + wordLen` addition overflow — the item
   previously left open — is closed by rejecting words of 31+ cells before the
   addition.
2. `advanceToLine`'s screen-full bound was **dead code**: 16-bit index mode makes
   `CPY #imm` three bytes, but it was emitted as two, swallowing the `BCC` opcode
   and neutering the guard. Word-wrap padding could therefore write a glyph past
   the 510-cell plane and into the attribute plane. Now a correct three-byte
   `CPY #$01FE`.
3. The caret cell is a **16-bit** value at `$0b`/`$0c` (index registers are
   16-bit here), and the word-length counter also lived at `$0c`. Every word
   measured after the caret was captured destroyed its high byte, so **no caret
   rendered at all unless the cursor was at the natural end of text**. The
   counter moved to `$5a`. This also resolves the open shift+arrow caret
   observation below — the host was never at fault.

New permanent coverage in `tests/snes_machine_tests.cpp` for all three, plus the
caret-on-active-selection-edge case. Full `ctest` is 10/10 and
`fairywriter_xband_end_to_end` passes 10 consecutive runs. The top-level app
bundle has been resynced and re-verified.

**Read the "Discoveries that constrain future work" section of `SCRATCH.MD`
before touching `renderDocument` again** — particularly that index registers are
16-bit there, that the pointer hit-test cannot resolve past cell 255, that the
pointer scratch comments are wrong by 6 for the `$034x` block, and that CMake
does not reliably regenerate the cartridge on this volume.

Not implemented this session: wrap-aware `Up`/`Down`. It reads the `$0b`/`$0c`
caret pair that was corrupt until fix 3 landed, so it was genuinely blocked. Its
design is fully specified in `SCRATCH.MD`'s next actions.

## 2026-07-26 rich style (bold/italic/underline) rendering

Implemented end to end. The host already transmitted these three format-run flags from real document formatting (`src/document_engine.cpp`'s fragment-format loop), but the ROM's projection loop masked them out (`AND #$18`) before they reached the per-cell style map. Fixed in `tools/fairywriter-rom/main.go`:

- Widened the mask to `#$1f` at both the projection loop and the draw loop's attribute-selection code, gated by a real `richStyleVisualsEnabled` switch (setting it `false` reverts the mask to `#$18` and skips generating the extra tiles -- unlike the pre-existing `proofingVisualsEnabled`, which was found to be declared but never actually referenced anywhere).
- Added three new 128-tile glyph-shape pages (ids 128-255 underline, 256-383 bold, 384-511 italic) via `glyphShapePixels()`, generated by pixel-transforming the existing resident font: underline lights the glyph's unused 8th pixel row; bold dilates every lit pixel 1px right; italic skews rightward by up to 2px, more at the top row. Base glyphs are only 5 columns wide, so none of this clips into a neighboring cell.
- Encoding: shape-index (0 plain/1 underline/2 bold/3 italic) splits across tile-low-byte bit7 (shape's low bit) and attribute-byte bit0 (shape's high bit, i.e. tile-id char-bit8). **This bit-splitting was verified empirically against the actual emulator core**, not just reasoned about statically: a temporary diagnostic placed a distinct checkerboard tile at id 321 (='A'+256) and confirmed via a framebuffer dump that setting attribute bit0 really does make the PPU fetch that tile instead of 'A'. Palette (proofing color, bits 4-2) and shape (style, bits 1-0) are independent fields in the same attribute byte and combine correctly on the same cell (bold+spelling, underline+spelling both verified).
- Priority when more than one style bit is set on the same run: underline > bold > italic (a product choice, confirmed working, open to revisiting). Selection continues to take priority over both proofing and style.
- The ROM's static-data layout shifted `+0x100` (`menuOffset` through `tilesOffset`) to fit the larger draw-loop program -- ~13KB of slack before `scanMapOffset` absorbed it with no cascading risk. Two branches that used to fit in one 8-bit relative jump no longer do with the styled path in between; both now use the standard 65816 long-branch trampoline (inverted condition, skip over an absolute `JMP`).
- Verified: new permanent tests in `tools/fairywriter-rom/main_test.go` and `tests/snes_machine_tests.cpp` (8 flag-combination cases including priority and proofing-combination), plus a direct framebuffer/PPM visual dump showing "PLAIN BOLD ITALIC UNDERLINE" clearly and legibly distinct at native 8x8 resolution. Full `ctest` is 10/10.

## 2026-07-26 selection-highlight fix (later session)

Restored text-selection highlighting after confirming (via `git show 58c1d5d`) it was silently deleted when the proofing split-path landed, and after diagnosing — empirically, via a temporary `fairy_snes_debug_wram`-based diagnostic in `tests/snes_machine_tests.cpp`, not just static reading — that the old code's zero-page addresses (`$19`/`$1b`) can't be reused as-is: `$19` is reused by the draw loop's own word-wrap measurement code, and `$1b` is reused by title-bar rendering (`"bounded resident title byte count"`), both within the same commit/render pass, so a decode-time write to either is guaranteed to be stomped before the draw loop can read it back. Fixed by moving selection-bounds tracking to `$50`/`$52` (confirmed free), with selection rendering via the existing spelling-issue attribute value and taking priority over proofing on the same cell. Manually confirmed live in the app: selecting text highlights it (solid blue fill/orange glyph), and collapsing the selection removes the highlight. One separate, pre-existing nuance observed but not investigated: the blinking caret glyph appeared to stay at the document end rather than tracking the active edge during a shift+arrow selection — a different code path (`$00`/`$0b` caret rendering), untouched by this fix.
